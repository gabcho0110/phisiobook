# Сигурност на PhysioBook

**Дата на проверката:** 11 октомври 2026
**Статус:** 🔴 Отворен проблем с висока тежест

---

## 1. Резюме

Базата данни на PhysioBook (Firebase Realtime Database, проект `physiobook-d6eff`)
е **публично достъпна за четене без никаква автентикация**.

Всеки човек в интернет може да прочете медицинските досиета на всички пациенти,
списъка с потребители и администратори и техните кодове за вход.

## 2. Доказателство

Направена е неутрална заявка, която връща **само имената на top-level възлите**,
без самите данни:

```bash
curl "https://physiobook-d6eff-default-rtdb.europe-west1.firebasedatabase.app/.json?shallow=true"
```

Резултат:

```json
HTTP 200
{
  "adminSettings": true,
  "users": true,
  "superAdmins": true,
  "admins": true,
  "clinics": true,
  "upgradeRequests": true,
  "notifications": true,
  "clinicSettings": true
}
```

Сървърът отговаря `200 OK` **без токен за автентикация**. Това означава, че
правилата на базата са отворени.

**Потвърдено на 11.10.2026** чрез четене на самите правила (с service account):

```json
{
  "rules": {
    ".read": true,
    ".write": true
  }
}
```

Това е конфигурацията „test mode" по подразбиране. **Записът също е отворен** —
всеки може не само да чете, но и да **променя и изтрива** всички данни.

## 3. Какво е изложено

| Възел | Какво съдържа |
|---|---|
| `clinics/{id}/patients` | Медицински досиета: диагнози, анамнеза, медикаменти, алергии, ЕГН, телефони, имейли, адреси |
| `clinics/{id}/users` | Потребители и техните **`accessCode` (кодове за вход)** в явен вид |
| `users`, `admins`, `superAdmins` | Потребители, администратори и техните кодове |
| `clinics/{id}/…` | Графици, процедури, ваучери, инвентар, съобщения, нотификации |
| `upgradeRequests`, `notifications` | Заявки и известия |

## 4. Влияние

- **GDPR, чл. 32** (сигурност на обработката) — нарушен. Данните за здраве са
  **специална категория лични данни** (чл. 9) и изискват най-висока защита.
- **GDPR, чл. 33** — при такава експозиция може да има задължение за уведомяване
  на надзорния орган в срок от 72 часа.
- Кодовете за вход са публично четими → всеки може да влезе като всеки потребител.
- Възможно е и неоторизирано изменение/изтриване на данни.

## 4.1 🔴 Допълнителна дупка: вход в админ панела с код `123456`

`admin.html` съдържаше функция `ensureProtectedAdmin()`, която **при всяко
зареждане създаваше** администраторски запис с **твърдо зададен код**:

```js
const DEFAULT_ADMIN_CODE = '123456';
const PROTECTED_ADMIN_ID  = 'physiobook_admin';
```

Проверено в реалната база на 11.10.2026:

| id | име | роля | защитен | кодът е `123456` |
|---|---|---|---|---|
| `physiobook_admin` | PhysioBook Admin | super | да | **ДА** |
| `-P2mgpip-mc7PX5ZyRoQ` | Алекс Тодоров | super | — | не |
| `-P2mgu6hPEUCs4JV5qNP` | Габриел Атанасов | super | — | не |

**Влияние:** всеки човек в интернет може да отвори `admin.html`, да въведе
`123456` и да получи **пълен супер-администраторски достъп** — да създава и
трие клиники, да вижда всички пациенти, да променя кодове. Дупката е активна
в момента, не само теоретична. Допълнително: дори записът да бъде изтрит,
той се пресъздаваше автоматично при следващо зареждане.

**Поправено в този клон:** функцията вече не създава нищо автоматично.

**Остава за вас:** премахнете или преименувайте акаунта `physiobook_admin`
(или сменете кода му) — кодът `123456` е публично известен.

## 5. Защо проблемът не се решава с „просто заключване на базата"

Това е важно да се разбере, преди да се пипат правилата.

В момента приложението работи така:

1. При зареждане `index.html` се абонира за **целия** възел `clinics`
   (`onValue(clinicsRootRef)` — функция `startClinicsListener()`).
2. Потребителят въвежда 6-цифрен код.
3. Клиентът търси този код сред **всички** потребители и пациенти на всички клиники
   (`findUserByCodeInAllClinics`).
4. Ако го намери — „влиза".

Тоест **автентикацията се извършва изцяло на клиента**, а за да работи, клиентът
трябва да може да прочете цялата база. Затова:

- Ако се сложи `.read: false` → входът спира да работи.
- Ако се сложи `.write: false` → нищо не може да се записва (пациенти, графици и т.н.).
- Няма Firebase Authentication, значи правилата не могат да разграничат кой е
  потребителят — всеки е „анонимен".

**Изводът:** истинската защита изисква въвеждане на Firebase Authentication.
Самите правила не могат да „поправят" липсата на автентикация.

## 6. Ограничение: кодовете не трябва да се сменят

Кодовете са постоянни за всеки потребител и не трябва да се ротират — те са
идентификаторът му. Затова решението **не** включва генериране на нови кодове.

## 7. Варианти за отстраняване (без смяна на кодовете)

### Вариант A — Firebase Auth (имейл/парола, без сървър) ⭐ препоръчан за начало

Идея: за всеки потребител се създава Firebase Auth акаунт, където
**имейлът и паролата се извеждат от самия код**:

```
email    = "{code}@physiobook.eu"     напр. 123456@physiobook.eu
password = "{code}"                    напр. 123456
```

- ✅ Кодовете остават **същите** — нищо не се сменя
- ✅ Въвежда се истинска автентикация → правилата могат да пазят данните
- ✅ Не е нужен сървър за работа (Firebase Auth е managed услуга)
- ✅ Firebase Auth има вградено ограничаване на опитите (за разлика от публичен API)
- ⚠️ Паролата е 6 цифри (слабовата е), но не по-слаба от сегашния модел, а
  атакуващият вече **не може да изтегли кодовете наведнъж**

**Стъпки:**

1. Firebase Console → **Authentication** → Sign-in method → включи
   **Email/Password**.
2. Еднократен скрипт с Admin SDK (service account ключ), който за всеки
   потребител/пациент създава Auth акаунт с горните имейл и парола и записва
   `uid` към съответния запис.
3. В `index.html` входът се сменя на:
   ```js
   import { getAuth, signInWithEmailAndPassword } from
     "https://www.gstatic.com/firebasejs/10.12.2/firebase-auth.js";

   const auth = getAuth(app);

   async function attemptLogin() {
     const code = Array.from(codeInputEls).map(i => i.value).join('');
     if (code.length !== 6) { showLoginError('Въведете пълен 6-цифрен код.'); return; }
     showLoading(true);
     try {
       await signInWithEmailAndPassword(auth, `${code}@physiobook.eu`, code);
       // ... съществуващата логика след успешен вход
     } catch (err) {
       showLoading(false);
       showLoginError('Грешен код. Опитайте отново.');
       clearCodeInputs();
     }
   }
   ```
4. Правилата се заключат (виж §8).
5. Старият `accessCode` се маха от клиентските записи (или поне от четения от
   клиента достъп), за да не изтича.

### Вариант B — Cloud Functions + custom tokens (най-стабилен)

- Cloud Function `login(code)` проверява кода **на сървъра** (срещу защитен възел
  `loginIndex`, който клиентът не може да чете) и връща **custom token** с
  custom claims: `clinicId`, `role`, `userId`.
- Клиентът прави `signInWithCustomToken`.
- Правилата пазят данните по клиника: `auth.token.clinicId == $clinicId`.
- ✅ Кодовете остават същите
- ✅ Най-прецизна авторизация (роля, клиника, пациент)
- ⚠️ Изисква план **Blaze** и deploy на функции — по-голяма промяна

## 8. Правила за базата (не се прилагат, докато клиентът не е обновен!)

⚠️ **НЕ качвайте тези правила преди да е готов Вариант A или B** — входът ще спре.

Предложение за крайно състояние (с Firebase Auth):

```json
{
  "rules": {
    ".read": false,
    ".write": false,
    "clinics": {
      "$clinicId": {
        ".read": "auth != null",
        ".write": "auth != null"
      }
    },
    "users": { ".read": "auth != null", ".write": false },
    "admins": { ".read": "auth != null", ".write": false },
    "superAdmins": { ".read": false, ".write": false },
    "adminSettings": { ".read": "auth != null", ".write": "auth != null" },
    "upgradeRequests": { ".read": "auth != null", ".write": "auth != null" },
    "notifications": { ".read": "auth != null", ".write": "auth != null" }
  }
}
```

За Вариант B правилата могат да са по-строги, напр.:

```json
"clinics": {
  "$clinicId": {
    ".read": "auth != null && auth.token.clinicId === $clinicId",
    ".write": "auth != null && auth.token.clinicId === $clinicId"
  }
}
```

## 9. Незабавни действия (докато трае миграцията)

1. **Отворете Firebase Console → Realtime Database → Rules** и проверете дали
   `.write` също е `true`. Ако да — това е най-спешният риск (всеки може да
   изтрие данни). Ограничете поне записа, ако е възможно без да счупите app-а.
2. Проверете в **Authentication → Users** дали няма неочаквани акаунти.
3. Проверете **Realtime Database → Backups**, ако има налични.
4. Направете **експорт на данните** (JSON) за резервно копие преди всяка промяна.
5. Преценете дали имате задължение за уведомяване по GDPR чл. 33.

### 10.5 Какво предстои (Фаза 2)

Сега всяка автентикирана сесия може да чете данните на **всички** клиники.
Следващата стъпка е изолация по клиника:

- карта `userClinics/{uid} → clinicId`, четлива само от собственика си;
- правила от вида
  `"clinics/$clinicId": { ".read": "auth != null && root.child('userClinics').child(auth.uid).val() === $clinicId" }`;
- клиентът чете картата си и зарежда само своята клиника.

Алтернативата е Вариант B (custom claims през Cloud Function).
